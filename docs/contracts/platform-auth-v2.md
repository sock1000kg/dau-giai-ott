# Platform Authentication and Admin Security Contract v2

> **Status:** APPROVED policy contract for Phase 3; endpoint schemas/tests are delivered by `P3-D04` and `P3-D06`.
>
> **Compatibility:** extends v1 sessions/RBAC; no self-registration or unauthenticated password reset is added.
> Authenticated `TEAM_ACCOUNT` password change follows the v1 contract and revokes all sessions for that account.

## Bulk team provisioning

- Only `BTC_ADMIN` may import the BTC-approved CSV.
- Every row is validated before commit; duplicate team/email/username failures identify the row and the
  operation is atomic.
- The server creates random credentials and streams one plaintext credential file exactly once. Only hashes
  persist. Plaintext must not enter database, object storage, log, metric, trace or audit.
- Retrying the same completed operation never returns the previous plaintext. Bulk reset creates new
  credentials and revokes old sessions.

## BTC multi-factor authentication

- `BTC_ADMIN` authentication is password plus TOTP, with one-time recovery codes stored hashed/encrypted as
  appropriate. Used recovery codes cannot be replayed.
- TOTP secret/recovery material never appears in client bundle, log, metric, trace or audit.
- `TEAM_ACCOUNT` keeps the v1 login/session flow. Its authenticated password-change operation is defined in
  Platform Auth v1; it does not add a forgot-password or unauthenticated reset flow.

## Admin network boundary and startup guard

- Admin routes validate the effective client address only through explicitly trusted proxies and a configured
  LAN/VPN CIDR allowlist; spoofed forwarding headers are rejected/ignored.
- Dev/test may explicitly disable TOTP/allowlist. Hosted PoC and production must fail startup when TOTP is
  disabled, the allowlist is empty, or trusted-proxy configuration is ambiguous.
- Login/admin/upload/write routes have account/IP rate limits, body limits and security headers.

## Audit and failure behavior

- Audit records actor, operation, target/count, reason, correlation ID and timestamp, never secrets.
- Team password changes audit `TEAM_PASSWORD_CHANGED`; current/new passwords and password hashes are never
  written to audit, logs, metrics, traces or responses.
- Authentication errors do not disclose whether a username, TOTP enrollment or recovery code exists.
- Authorization remains server-side; UI visibility is never an access-control boundary.

## Implementation notes (P3-D06)

Decided contract additions delivered by `P3-D06`:

### Two-step login and MFA endpoint shape
- `POST /api/v1/auth/login`: team accounts and BTC admin with `totpRequired=false` authenticate directly into a session cookie (`ott_session`). When `totpRequired=true`, BTC admin password verification returns `200 { "data": { "mfaRequired": true } }` with a single-use `ott_mfa` HttpOnly cookie (5 min TTL, max 5 attempts).
- `POST /api/v1/auth/login/mfa`: strict body with either `{ "code": string }` (6 digits) or `{ "recoveryCode": string }` (16 Base32 characters formatted `XXXX-XXXX-XXXX-XXXX`). On success, destroys challenge, creates session cookie with `mfa: true`, and audits `AUTH_LOGIN_MFA` with method (`TOTP` or `RECOVERY_CODE`) in reason. On failure, returns uniform `401 INVALID_CREDENTIALS` without disclosing enrollment state.

### Enrollment and code formats
- **Bootstrap enrollment**: `bootstrapBtcAdmin` supports optional `OTT_BOOTSTRAP_BTC_TOTP_SECRET` (Base32) with `totpEncryptionKey` (32 bytes AES-256-GCM) to seed the initial BTC admin MFA secret. Recovery codes are not generated during bootstrap (to avoid unviewed codes) and should be generated by the operator via `POST /api/v1/auth/mfa/recovery-codes` after first MFA login.
- **Self-service MFA**:
  - `POST /api/v1/auth/mfa/enroll`: generates 20-byte Base32 secret and `otpauth://` URI (`Cache-Control: no-store`), temporarily stored as pending in Redis (10 min TTL).
  - `POST /api/v1/auth/mfa/confirm`: verifies `{ "code": string }`, encrypts and stores secret in `admin_mfa`, generates 10 recovery codes.
  - `POST /api/v1/auth/mfa/recovery-codes`: invalidates old unused recovery codes and generates 10 new recovery codes.
  - When `totpRequired=true`, MFA management requires the session principal to have `mfa: true`.
- **Replay and single-use protection**:
  - TOTP: atomic check-and-set on `admin_mfa.last_used_step` ensuring `step > last_used_step`.
  - Recovery codes: stored as SHA-256 of normalized code; consumed atomically via `UPDATE admin_recovery_codes SET used_at = now() WHERE code_sha256 = $1 AND used_at IS NULL RETURNING id`.

### Network boundary and write rate limiting
- Server-side `onRequest` guard blocks non-allowlisted client IPs on `/api/v1/admin/*` and `/api/v1/auth/mfa/*` with `403 ADMIN_NETWORK_FORBIDDEN`.
- `effectiveClientIp`: ignores `X-Forwarded-For` unless the socket peer is in `trustedProxies`.
- Write rate limits: 600 req/min per IP and 300 req/min per account for POST/PUT/PATCH/DELETE (excluding `/api/v1/auth/login*`), returning `429 RATE_LIMITED` with `Retry-After: 60`.
